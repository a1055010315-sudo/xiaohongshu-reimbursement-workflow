# 批次归档与展示规则

阶段 B 制作或验证文字说明、本次明细、截图归档及“报销明细对应截图表”时完整读取本页。批次状态、两道门禁、临时目录和发布以父级 `SKILL.md` 为准。

## 1. 唯一数据源与类目

使用父批次事实文件驱动全部产物；摘要、明细、截图表和候选校验不得分别重新解析材料。新任务中的明细 E、对应截图表“备注”和候选 F 必须投影同一个已冻结 `classification`，不允许分别归类。

- 只使用 `ledger-profiles.json` 中的 `xiaohongshu`、`company`、`residence`；从交易机械得出 `affectedProfiles`。一个类目自动退化为单账本，多个类目并行处理后统一进入门禁。
- 每笔记录恰属一个 profile；一张凭证可以通过多对多证据关系覆盖多笔或多个 profile，并只哈希、解码、识别一次。
- 本批涉及的每个 profile 都生成自己的明细、截图归档、截图对应页和候选；不再把公司或驻所仅作为“小红书非目标类目”隔离。
- 用户写出具体单子或项目名时，`classification` 使用该稳定名称，不得降级为 `日常报销`。事实或 `affectedProfiles` 变化使统一门禁失效。

## 2. 最终归档结构

父批次只统一取证、处理、门禁和发布状态，不建立跨专项公共归档。每个受影响 profile 仍写入其专项根目录下绑定的归档路径；用户明确要求延续上一周期时，扩展该 profile 已绑定的 `archivePath` 和周期终点，不新建或迁移归档。每个 profile 最终只保留下列交付物：

```text
<profile专项根目录>/报销/<时间段>_<profile显示名>/
├─ <时间段>_报销文字说明.txt
├─ <时间段>_本次报销明细.xlsx
├─ <时间段>_报销明细对应截图表.xlsx
├─ <profile归档stem>_截至<结束日期>.xlsx
├─ 发布审计.json
└─ 报销截图/<profile显示名>/
```

单 profile 时只创建该 profile 的明细、候选快照和截图目录；不要为另外两个 profile 创建空内容。多 profile 仍分别落入各自专项归档，展示和父工件按 `profileOrder` 排列。父 `batch-run`、Gate、缓存、预览和回滚材料只留在任务临时目录。

新普通任务使用 `minimal-current-only`：活动归档中每类正式交付物只保留一个当前版本；内部 manifest、证书、预览、缓存、日志、解析文件和回滚材料留在任务临时区。发布及发布后审计全部成功后清理临时材料，只保留精简 `发布审计.json`。旧任务或恢复任务使用 `legacy-history`，不得自动删除既有历史材料。

## 3. 活动版本晋升

所有新字节先在父级任务临时目录构建，完成语义、公式、格式、视觉和 SHA256 验收后才可成为当前候选。

1. `minimal-current-only` 不创建同级 `_历史版本`；被替代当前版本只进入任务回滚 staging，直到协调发布和发布后审计全部成功。
2. 发布失败、外部替换或无法证明归属时，保留精确 staging、journal、锁和恢复日志并阻塞，不删除现场。
3. `legacy-history` 继续使用既有 `promote_active_revision.mjs` 和 `audit_active_revisions.mjs` 兼容旧任务、重排和恢复；不得套用于新普通批次。
4. 统一门禁只绑定每个 profile 当前已验收候选的规范路径、修订号和 SHA256；任何候选字节或 profile 集合变化都使整个父批次门禁失效。

## 4. 摘要预览与门禁绑定

新版对每个受影响 profile 的 manifest v3 只读投影调用 `scripts/build_reimbursement_summary.mjs`，再按 `profileOrder` 机械拼接父批次预览；禁止人工维护第二套业务事实。`--input` 只用于兼容既有 v1 批次：

```text
"<bundled-node>" scripts/build_reimbursement_summary.mjs --manifest <batch-manifest.json> --preview
"<bundled-node>" scripts/build_reimbursement_summary.mjs --manifest <batch-manifest.json> --output <new-output.txt> --expect-sha256 <预览textSha256>
```

每个 profile 预览输出确定性的 `summary` 正文、`textSha256` 和金额摘要，不创建文件；父预览按固定顺序绑定这些摘要。阶段 B 一次展示全部受影响 profile，不等待额外自然语言确认。第一道统一门禁同时确认父摘要和其余核对包。收到门禁后才按各 profile 的预览哈希写入其专项归档最终 TXT；输入变化或哈希不一致时必须在创建文件前失败。

输入使用 manifest v3 的 `profile`；每个 entry 使用最多三位小数的有符号十进制字符串 `amount`、标签 `label` 和独立 `settlement`。`settlement` 只允许 `employee_reimbursement` 或 `company_paid_no_reimbursement`，不得由 profile 推断。负数必须引用同 profile、同结算方式的正金额来源交易。

格式要求：

- 每个实际受影响 profile 单独成段，按 `profileOrder` 排列；没有交易的 profile 不出现。
- 标题为 `<完整中文时间段><报销类目>`，例如 `2026年7月1日-7月13日公司报销`。
- 同一人员需实报的多笔合并一行；每个对公不实报对象单独汇总一行。段内不写项目、逐笔日期、备注、截图引用、路径或 SHA256。
- 标签和金额之间使用全角冒号 `：`；金额最多三位小数，保留有效精度，不加千位分隔符。
- 每个 profile 始终输出 `实报合计`；存在 `对公已付不实报` 时，在其前输出包含该 profile 全部支出的 `费用合计`。`实报合计` 排除该 profile 的对公已付。
- 时间段写完整中文日期并带年份；跨年时两端都写年份。
- 原义、人员或分类不明确时先确认，不得为凑平总额改写。

## 5. 本次报销明细

每个 profile 的本次明细只包含当前时间段属于该 profile 的交易，不得混入历史记录或其他 profile。它是供人审阅的人员分区视图，不承担候选导入职责。默认 A-F 为：

| 列 | 内容 |
|---|---|
| A | 日期 |
| B | 项目或费用明细 |
| C | 单笔金额 |
| D | 费用组合计 |
| E | 备注或分类 |
| F | 报销属性；普通实报或 `对公已付不实报` |

确定性分区和排序规则：

1. `settlement: employee_reimbursement` 按正式支出人建立连续区块；新任务按该人员最小 `sourceOrder` 排列，旧 manifest 只读恢复时才兼容旧数组顺序。
2. 每个区块内按合法 ISO 日期升序；同日保持 manifest 稳定来源顺序。人员分区后的全表日期可以回退，不能再要求全局日期升序。
3. 所有 `company_paid_no_reimbursement` 从普通人员区块移出，按对公主体/标签建立区块并放在普通人员区块之后；按最小 `sourceOrder`、区内日期升序排列。标题写为 `<主体>（对公已付不实报）｜<N>笔`。
4. 普通标题写为 `<人员>｜<N>笔`。标题行和空白分隔行是展示行，不是交易；只允许标题行的小计公式引用本区 C 列，不得进入业务多重集合、明细笔数、候选或根表。
5. 每笔本 profile 交易恰好出现一次，其他 profile 交易为零。业务匹配使用 `profile + 日期 + 项目 + Decimal 金额 + 人员/报销属性 + classification` 多重集合，不依赖行号。

版式严格使用 `workbook-style-contract.json`：三类支出明细都继承小红书语义布局；公司和驻所只使用声明的蓝色角色覆盖。顶部放置公式驱动的三张汇总卡，每个区块标题显示笔数和小计。允许同一费用组的 D/E/F 使用完全相同的纵向合并范围；锚点居中、垂直居中、自动换行，D 为精确组内 SUM，非锚点在 OOXML 中为空。超 7 行或 210pt 的块专项预览但不自动拆分。

候选和根表使用 profile 的固定 A-F 语义及共同样式契约；不得导入人员标题、空白分隔行或展示用辅助结构。映射不可靠时按 Excel reference 阻塞。

## 6. 原图归档

在 `报销截图` 下只为实际受影响 profile 建立显示名文件夹。

- 复制原始文件内容和扩展名；重名时加稳定编号，不覆盖、不裁剪、不压缩，不用 OCR 文本替代。
- 一张图覆盖多个 profile 时，每个相关目录各保留一份原图副本，在 manifest 标记共享来源；识别缓存仍只保存一份。
- 每个归档副本都与已登记的来源 SHA256 比较；来源本就在正确目标位置时不重复复制。

## 7. 对应截图表

对话版和本地 `.xlsx` 必须使用同一组逐笔记录、冻结 `classification` 和图片顺序；对应表不得在展示阶段重新猜测分类。

- “页”只指可见 Sheet。只为 `affectedProfiles` 创建页，并按 `profileOrder` 排列；单 profile 只有一个业务页。
- 不得为 manifest、审计或调试增加隐藏 Sheet；内部检查点留在任务临时目录。
- 每个 Sheet 使用 `日期｜支出人/主体｜项目｜金额｜备注｜图1｜图2｜…`。列名必须是 `备注`，它放在全部图片列之前。
- 每张图单独占一个 `图N` 列，同一单元格不得纵向堆叠多图。直接付款/业务凭证在前，财务文字说明或拆分依据在后；没有图片的后续列留空。
- 图片必须嵌入，不得用外链、文件名或路径代替。保持宽高比和内边距，设置足够列宽/行高，确保图片、金额和备注无裁切、遮挡或跨行。
- 同一凭证覆盖多笔时可在相关业务行放置独立锚点；图片哈希相同不能成为删除业务行的理由。实现支持时复用同一 OOXML media part，避免重复写入相同图片字节。

## 8. 一次展示与视觉验收

阶段 A 只给疑点附图。对应截图表完成语义和视觉验收后，在对话中完整展示一次；所有分批合起来必须覆盖每笔记录和每张采用图片，不能只给路径或来源编号。后续哈希未变化时不再重复展示。

验收分为两部分：

1. **全量自动检查**：重新打开工作簿，一次遍历核对 Sheet 顺序、逐笔行数、每行 `图N` 锚点、嵌入实例数、图片 SHA256 映射、行列边界、数字精度和公式错误。
2. **有界视觉检查**：为每个 Sheet 生成覆盖全部实际数据行的紧凑联系预览；另检查首行、中间行、末行、图片最多行和布局变化边界。发现裁切、重叠、越界或布局变化时才全尺寸渲染受影响区块，禁止把 Sheet 数误当打印/PDF 页数，也禁止渲染大量空白格式行。

用户在一次展示后纠正任何业务内容时，只重建受影响交易及下游产物；未变化图片继续复用原视觉核验。
