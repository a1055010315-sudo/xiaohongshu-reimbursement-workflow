阶段 B 制作或验证文字说明、本次明细、截图归档及“报销明细对应截图表”时完整读取本页。批次状态、两道门禁、临时目录和发布以父级 `SKILL.md` 为准。

## 1. 唯一数据源与类目

使用当前任务的 `batch-manifest.json` 中同一组规范化交易驱动全部产物；摘要、明细、截图表和候选校验不得分别重新解析材料。新任务中的明细 E、对应截图表“备注”和候选 F 必须投影同一个已冻结 `classification`，不允许在三个产物中分别归类。

- 只用 `references/ledger-profiles.json` 把每笔交易路由到 `xiaohongshu`、`company` 或 `residence`；不得由调用方临时指定“目标/非目标”类目。
- 每个受影响 profile 独立生成摘要、明细、截图表、根表候选及发布产物；其他 profile 的交易不得进入当前 profile，未受影响 profile 不生成空文件。
- 每笔记录只能有一个 canonical profile；一张凭证可以通过多对多证据关系覆盖多笔或多个 profile。
- `classification` 可直接使用的通用值仅为 `运营开支`、`日常报销`、`人员工资`、`社保`、`房租`、`广告费`。其他值只可作为具体项目名；即使材料中已出现该名称，也必须在 manifest 冻结前由用户在当前对话明确指定或确认，不能用规则表、模型判断或持久化授权字段代替。`单子名`、`中转站`、`节点`、`话费`、`手机充值`、`手机话费`、`数字人`、`Codex` 是费用描述或占位字面值，`上海天崇`、`东莞柯南` 是主体/地点字面值，均不得直接作为分类；应按费用性质映射，本批已确认的东莞柯南地址费归 `日常报销`。经用户明确授权的具体项目名示例可为 `广东嘻箱记`、`上海李忧忧`、`随州侯女士`。分类变化必须先回写 manifest 交易并使所有下游摘要、候选和门禁失效。

## 2. 最终归档结构

归档文件夹最终只保留下列交付物：

```text
<manifest.batch.archivePath>/
├─ 01_小红书专项/                 # 仅本批有小红书交易时
├─ 02_公司专项/                   # 仅本批有公司交易时
└─ 03_住所专项/                   # 仅本批有驻所/住所交易时

<受影响 profile 专项目录>/
├─ <时间段>_<canonical类目>_报销文字说明.odt
├─ <时间段>_<canonical类目>_本次报销明细.xlsx
├─ <时间段>_<canonical类目>_报销明细对应截图表.xlsx
├─ <时间段>_<canonical类目>_候选总表.xlsx
├─ <时间段>_<canonical类目>_报销截图/
├─ <时间段>_<canonical类目>_补报表.xlsx       # 仅本批有补报时
└─ <时间段>_<canonical类目>_补报凭证/         # 仅有独立补报凭证时
```

正式交付物是：留在根目录的正式总表、文字说明、三份业务表（本次报销明细、报销明细对应截图表、候选总表）和截图凭证目录。候选总表就是本批提交时的第三份业务表，不再额外复制一份语义重复的“快照.xlsx”。有补报时额外生成独立补报表；只有独立补报凭证时才建立补报凭证目录。无补报时不得生成空补报表或空补报目录。活动归档中每类正式交付物只保留一个当前版本；带不同 `_修正版N` 后缀的同类文件仍属于同一交付物类型，不能并列成为当前版本。不要留下 manifest、验收证书、自动生成的 `.inspect.ndjson`、差异说明、聊天区间辅助目录、预览、日志、解析文件或构建脚本。已经交付或验收过的旧版不得删除；按第 3 节完成版本晋升，避免通配符同时选中两个当前文件。

## 3. 活动版本晋升

新修正版先在父级专用任务临时目录构建；完成语义、公式、格式、视觉和 SHA256 验收前，不得放入活动归档。验收通过后按以下顺序晋升：

1. 精确枚举同一交付物类型的活动当前版本，确认来源恰好一个；首次生成时确认当前版本为零。确定单调递增且未占用的 `_修正版N`，不得覆盖任何现有文件。
2. 在活动归档同级使用 `<归档文件夹名>_历史版本/`。先检查历史目标路径不存在；重名、归属不明或多个当前版本时阻塞，不自动改名或删除。
3. 只用 `scripts/promote_active_revision.mjs` 执行晋升：候选和历史快照均先写入事务私有 staging、fsync 并验 SHA256，再以原子 hardlink/rename 安装；旧当前版本的可恢复 staging 必须使用预验哈希后的原子 rename。历史快照不得与活动文件共用硬链接，避免外部原地写同时破坏两份。
4. 晋升器和审计器在整个文件族操作期间持有同一 Windows Local named Mutex；PowerShell helper 经 stdin 持锁，父进程 kill 后自动释放，超时或 helper 异常在写前阻塞。完整原子安装的 v4 owner/PID/start-identity lock、v2 recovery guard 和事务 marker 记录提交点；进程崩溃后以同一 plan 重试恢复。普通失败自动还原，检测到外部替换或任何无法证明归属时保留旧版快照、锁和恢复日志并停止，不进入展示、门禁、发布或交付。
5. 晋升结束后用 `scripts/audit_active_revisions.mjs` 再次枚举：该交付物类型在活动归档必须恰好一个当前版本，其 SHA256 必须等于验收结果；旧版只在历史目录且哈希不变。该文件族存在任何 lock/recovery/marker 残留时审计也必须 fail-close，先用同一 promotion plan 完成恢复，否则阻塞。

门禁只绑定成功晋升后的当前候选路径、候选修订号和 SHA256。晋升造成候选字节或哈希变化时，两道门禁失效并重新从完整展示开始。

## 4. 摘要预览与门禁绑定

新版直接让 `scripts/build_reimbursement_summary.mjs` 审计并机械投影 `batch-manifest.json`，禁止手工拼接第二套业务事实；`--input` 只用于兼容既有 v1 批次：

```text
"<bundled-node>" scripts/build_reimbursement_summary.mjs --manifest <batch-manifest.json> --preview
"<bundled-node>" scripts/build_reimbursement_summary.mjs --manifest <batch-manifest.json> --output <new-output.txt> --expect-sha256 <预览textSha256>
```

预览模式输出确定性的 `summary` 完整正文、`textSha256` 和金额摘要，不创建文件；该命令的 `--output` 仅用于生成受绑定的中间文字核验，不是最终交付物。阶段 B 直接把完整正文贴在对话中；不要等待单独的自然语言确认。第一道精确门禁同时确认该摘要和其余业务核对包，主工作流随后把同一正文写入最终 OpenDocument 文字说明 `.odt`；输入变化或哈希不一致时必须在创建文件前失败。

普通报销 Gate v2 的 `previewScopes` 是候选和图片预览的唯一范围合同。`profileId` 只能使用 registry 的 canonical 小写值 `xiaohongshu`、`company` 或 `residence`。聚合 Gate 为每个 profile 建立独立子 context，其 `affectedProfileIds` 必须恰为 `[profileId]`，scopes 只含该 profile 的全部 root、恰一个 detail 和恰一个 screenshot；候选路径、修订号、候选 SHA 和 plan SHA 按 profile 独立绑定，批次 ID、操作摘要和来源覆盖摘要保持批次一致。允许把同一候选的本批增量根表拆成多个非连续 root scope（每个 profile 最多 10 段，整个请求最多 36 个 scope）。每个 scope 只接受并完整绑定 `profileId`、角色、工作表、矩形 A1 `rangeAddress`、源文件 `sourceSha256` 和渲染后 `previewSha256`；缺失、多余字段、重复角色、profile 集合不一致或 SHA 不一致都必须失败。root scope 只能覆盖审计给出的本批新增 `manifestRowRanges`（不含根表表头），其 `sourceSha256` 必须等于当前 profile 候选 SHA，同一工作表的 root scopes 不得越界或重叠。Gate 1→Gate 2 必须按 `profileId + role + sheetName + rangeAddress + sourceSha256` 完整身份配对，禁止依赖数组位置，缺失、重复或陈旧身份均失败。新的候选修订或候选字节变化会使旧预览立即失效。PowerShell renderer 在打开前、渲染期间和完成后重新核对源 SHA，并核对每个 PNG 的绑定 SHA；用户总表预览不得展示历史行。

正常明细始终使用 detail 合同。补报只在存在补报交易时通过显式 `getSupplementContract()` 额外生成独立补报表，在补报说明区填写原始发生日期、补报原因和关联原始凭证/来源编号；不得替换正常明细或把说明附在其尾部。独立补报凭证必须由补报交易显式提供非空 `supplementEvidence`，它必须是该交易 `evidence` 中图片 ID 的无重复子集；该交易还必须保留至少一张不在该子集中的普通图片凭证。没有 `supplementEvidence` 时所有图片都归入正常截图目录，不得仅因交易是补报就移入补报凭证目录。历史模板仅作视觉回归夹具。补报内容仍须转换为 manifest v3 的规范化交易，不能直接作为根表事实。

每个新版 transaction 使用 canonical `profileId/category`、最多三位小数的有符号字符串金额 `amount`、标签和独立结算枚举 `settlement`。`settlement` 只允许 `employee_reimbursement` 或 `company_paid_no_reimbursement`；旧版机械投影仍可用 `reimbursable`，两者同时出现时必须一致。负数必须附带引用同 profile、同类目、同结算方式正金额来源的 `adjustment`。每个 profile 的费用与实报合计都从其实际交易独立重算。

格式要求：

- 每个 profile 的文字说明只含该 profile 的 canonical 类目，profile 顺序固定使用 registry 顺序。
- 标题为 `<完整中文时间段><报销类目>`，例如 `2026年7月1日-7月13日公司报销`。
- 同一人员需实报的多笔合并一行；每个对公不实报对象单独汇总一行。段内不写项目、逐笔日期、备注、截图引用、路径或 SHA256。
- 标签和金额之间使用全角冒号 `：`；金额最多三位小数，保留有效精度，不加千位分隔符。
- 每个受影响 profile 都输出自己的 `费用合计` 和 `实报合计`；`实报合计` 排除该 profile 的 `对公已付不实报`。
- 不把其他 profile 的金额汇入当前 profile 的摘要或根表。
- 时间段写完整中文日期并带年份；跨年时两端都写年份。
- 原义、人员或分类不明确时先确认，不得为凑平总额改写。

## 5. 本次报销明细

每份本次明细只包含当前时间段、当前 canonical profile 的本批交易；不得包含历史记录或其他 profile。它是供人审阅的“人员分区视图”，不承担候选总表导入职责。默认 A-F 为：

| 列 | 内容 |
|---|---|
| A | 日期 |
| B | 项目或费用明细 |
| C | 单笔金额 |
| D | 费用组合计 |
| E | 备注或分类 |
| F | 报销属性；普通实报或 `对公已付不实报` |

确定性分区和排序规则：

1. `settlement: employee_reimbursement` 的普通实报交易按正式支出人建立连续区块；v2 人员区块按该人员最小 `sourceOrder` 排列，兼容读取 v1 时才使用 manifest 数组顺序。
2. 每个区块内按合法 ISO 日期升序；同日保持 manifest 稳定来源顺序。人员分区后的全表日期可以回退，不能再要求全局日期升序。
3. 所有 `settlement: company_paid_no_reimbursement` 交易从普通人员区块移出，按对公主体/汇总标签建立独立区块并统一放在全部普通人员区块之后；v2 这些区块也按最小 `sourceOrder`、区内日期升序排列，v1 兼容读取使用数组顺序。标题写为 `<主体>（对公已付不实报）｜<N>笔`。同一标签同时存在两种结算方式是合法业务，不得因标签相同而拒绝或混为一组。
4. 普通标题写为 `<人员>｜<N>笔`。标题行和空白分隔行是展示行，不是交易；只允许标题行的小计公式引用本区 C 列，不得进入业务多重集合、明细笔数、候选或根表。
5. 当前 profile 每笔交易恰好出现一次，其他 profile 交易为零。业务匹配使用 `日期 + 项目/费用明细 + Decimal 金额 + 人员/报销属性 + 备注/分类` 的多重集合，不依赖明细行号。

版式沿用已批准的样式：顶部放置公式驱动的 `实报合计`、`对公已付不实报` 和 `费用合计` 三张汇总卡；每个区块标题显示笔数和公式驱动的小计。D 列的同费用组合计只在组内首行写公式，续行留空，不为展示目的把业务行纵向合并。整体以绿色为基础，只对 `对公已付不实报` 区块使用浅橙提示色。金额完整显示用户确认精度，最多三位小数；长文字可做最小列宽调整。

候选和根表继续沿用其自身 A-F 列语义、日期排序、合并与样式；不得把本节的人员标题、颜色、空白分隔行或列位变化传播过去。基线或业务字段不能可靠映射时按 Excel reference 询问。

## 6. 原图归档

每个受影响 profile 在自己的专项目录 `报销截图` 下归档该 profile 实际引用的原图；不同 profile 共用同一来源时分别复制并核对同一 SHA256。

- 复制原始文件内容和扩展名；重名时加稳定编号，不覆盖、不裁剪、不压缩，不用 OCR 文本替代。
- 一张图覆盖多个类目时，每个相关类目各保留一份原图副本，并在 manifest 标记共享来源。
- 每个归档副本都与已登记的来源 SHA256 比较；来源本就在正确目标位置时不重复复制。
- 只有显式列入 `supplementEvidence` 且未同时作为普通凭证使用的额外图片进入条件性的 `补报凭证` 目录；不得创建空目录。

## 7. 对应截图表

对话版和本地 `.xlsx` 必须使用同一组逐笔记录、冻结 `classification` 和图片顺序；对应表不得在展示阶段重新猜测分类。

- “页”只指可见 Sheet，不是打印页或 PDF 页。每个 profile 的截图对应表只有 registry 指定的一个 canonical 可见 Sheet；不得把多个 profile 合并到 Sheet1/Sheet2。
- 不得为 manifest、审计或调试增加隐藏 Sheet；内部检查点留在任务临时目录。
- 每个 Sheet 使用 `日期｜支出人/主体｜项目｜金额｜备注｜图1｜图2｜…`。列名必须是 `备注`，它放在全部图片列之前。
- 每张图单独占一个 `图N` 列，同一单元格不得纵向堆叠多图。直接付款/业务凭证在前，财务文字说明或拆分依据在后；没有图片的后续列留空。
- 图片必须嵌入，不得用外链、文件名或路径代替。保持宽高比和内边距，设置足够列宽/行高，确保图片、金额和备注无裁切、遮挡或跨行。
- 同一凭证覆盖多笔时可在相关业务行放置独立锚点；图片哈希相同不能成为删除业务行的理由。实现支持时复用同一 OOXML media part，避免重复写入相同图片字节。

## 8. 一次展示与视觉验收

阶段 A 只给疑点附图。对应截图表完成语义和视觉验收后，在对话中完整展示一次；所有分批合起来必须覆盖每笔记录和每张采用图片，不能只给路径或来源编号。后续哈希未变化时不再重复展示。

验收分为两部分：

1. **全量自动检查**：重新打开工作簿，一次遍历核对 Sheet 顺序、逐笔行数、每行 `图N` 锚点、嵌入实例数、图片 SHA256 映射、行列边界、数字精度和公式错误。
2. **有界视觉检查**：为每个 Sheet 生成覆盖全部实际数据行的紧凑联系预览；另检查首行、中间行、末行、图片最多行和布局变化边界。发现裁切、重叠、越界或布局变化时才全尺寸渲染受影响区块，禁止把 Sheet 数误当打印/PDF 页数，也禁止渲染大量空白格式行。

用户在一次展示后纠正任何业务内容时，只重建受影响交易及下游产物；未变化图片继续复用原视觉核验。
