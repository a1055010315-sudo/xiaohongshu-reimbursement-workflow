# 微信证据核对规则

仅在报销材料来自微信聊天、合并转发记录或聊天截图时读取本文件。目标是在可审计边界内完整识别证据，不是翻阅完整个人聊天历史。

## 1. 固定本批边界

- 合并转发记录：以该记录打开后可见的首条至末条为边界；从首条连续检查到末条。
- 普通聊天：以本批明确的聊天对象，以及报销时间段或用户指定消息区间为主边界；只读取解释边界消息和款项关系所必需的相邻上下文。边缘仍有截断、引用或付款线索时逐段扩展，到达明确日期、话题或消息区间边界即停止。
- 文件或导出的聊天材料：以用户指定文件、页码或附件集合为边界。
- 无法判断首末边界或聊天中混有多个批次时，先询问用户；不得用“从头到真实底部”指代整段个人聊天历史。
- 离开材料源前回到已定义的末端，确认已经到达该末端，且末端附近没有仍属于本批的未登记图片、付款卡片、回单、附件或业务文字。有新增材料时更新边界和清单，并使旧计数和对应关系失效。

## 2. 一次收集，再做本地核验

1. 在微信中先固定本批起点和末端，再从起点连续浏览到真实末端。到达末端后确认附近没有仍属于本批但尚未登记的后续图片、付款卡片、回单、附件或业务文字；这里的“真实末端”只针对已定义的本批区间，不扩大到无关聊天历史。
2. 在这一遍浏览中同时分配来源编号、保存边界内全部候选原图/附件、登记业务文字和消息位置。原图保存到本任务专用临时目录根层；业务文字复制为带消息时间/来源编号的本地记录。聊天里不能直接导出的文字用完整区间截图或逐条本地摘录保留，不凭记忆转写。保存后等待精确目标文件关闭且大小稳定，不为每张图反复扫描整个临时目录。
3. 离开微信前一次比较候选数、已保存数和末端状态。任何候选尚未保存或末端尚未确认时，不得开始“全部对应”核对。图片哈希和尺寸可以在 2–4 个有界后台任务中随保存流水计算，但不能并行操控同一个微信窗口。
4. 后续逐图放大、金额识别、重复判断、截图对应表、对话展示、分类归档和工作簿构建都使用这些本地文件；同一批材料不得为了“再次核对”或“再次归档”重复进入微信读取。
5. 只有本地文件缺失、不可读、聊天截图存在被截断的关键上下文，或用户明确补充了新材料时才返回微信补取。补取后重新枚举本批清单并按路径、大小和 SHA256 做差分；只重新打开新增或内容变化的材料，未变化原图复用既有完整视觉检查。受影响的计数、对应关系和下游状态立即失效。

## 3. 建立材料清单

为边界内可能相关的材料分配稳定来源编号，例如 `WX-T01`（文字）、`WX-I01`（图片）、`WX-C01`（付款卡片）或 `WX-A01`（附件）；长图、复合截图和参考表还要为每个可独立处置的区域/业务行分配来源单元 ID。新任务把区间边界写入 manifest v3 的 `sourceScopes`，把每个来源单元写入 `sourceUnits`，并记录：

- 来源位置或可复现的消息时间；
- 本地绝对路径、文件大小、SHA256 和可读尺寸；
- 材料类型、候选数、已检查数和处置状态；
- 与人员、项目或其他材料的初步关系；
- 是否为原图、复合截图、转发缩略图或不可打开的静态嵌套区域。
- 唯一处置：被交易采用、已唯一存在于基线，或带原因排除为非目标类目；无法唯一处置时阻塞，禁止仅保存“排除行号”。

同一图片含多个候选区域时再编号为 `WX-I01-R01`、`WX-I01-R02` 等，使内部对应关系精确到“来源 + 图内区域”，不能只追溯到整张图。

陌生项目名或未预期的费用类型也先列为候选，不能因为不符合已有印象而跳过。明显无关的私人聊天不进入清单。

## 4. 检查完整画面

1. 打开可取得的原图或最高可读分辨率，不以聊天缩略图或 OCR 结果代替人工视觉检查。
2. 对长图和复合截图从上到下、从左到右检查；每个付款区域、转账卡片、回单、金额行和状态行都单独登记。无法在可读大小下一次看全时分段查看，相邻分段保留重叠，并明确覆盖图片首尾。
3. 静态截图里嵌入的图片通常不能继续“打开”。检查其可见区域；关键字段不清晰时索要原图、可读放大图或对应局部截图。
4. 截图顶部、底部和边缘必须纳入检查，不能因画面中部已有明显金额就停止。

## 5. 从图片规范化交易

截图数量不等于交易数量。对每个可能相关的金额候选记录可见的金额、时间、参与方、方向、状态和交易/订单标识，再分类为：

- 独立实际付款；
- 退款或退回；
- 优惠、抵扣、余额或商品原价；
- 计算式、合计或跨类目拆分项；
- 同一交易的重复截图或不同状态；
- 与本批无关的数字。

只有“独立实际付款”或经用户明确确认应入账的记录进入报销金额。退款或退回保留为独立的有符号调整记录，必须引用对应正金额来源交易和退款证据，不能只把原付款金额改小。不要只按金额相等去重：两个同额付款可能因时间、参与方、交易标识或上下文不同而是两笔；反过来，多张不同界面的图片也可能只是同一笔交易。

`已被接收`、`已收款`、`对方已领取` 等状态词只描述当前界面的局部状态，不能单独确定谁垫付、谁收款、交易方向或交易笔数。结合聊天气泡方向、当前账号、参与方、时间、交易标识和必要上下文判断；仍不唯一时提出附图问题。

## 6. 使用字段级证据

每笔规范化交易至少关联：稳定交易 ID、`sourceOrder`、正式姓名、项目、有符号金额、日期、报销类目、目标总表最终 `classification`、独立的 `settlement` 结算方式、证据类型/角色/顺序、`sourceRefs`、图内区域和本次明细行。聊天名或简称只保存在本批别名映射中，输出账表使用确认后的正式姓名。分类必须在 manifest 冻结前由字段级证据确定；六个通用值之外的具体项目分类还必须由用户在当前对话明确指定或确认，字段证据不能代替该授权。构建候选时不得再次从项目文字、人员或行号推断、泛化或改写。

- 付款截图、转账卡片或银行回单证明其中可见的客观付款字段。
- 用户业务说明证明人员、项目、报销类目、`classification`、`settlement` 结算方式和必要的业务关系；不能用类目名称推断结算方式，也不能把明确单子名降级为 `日常报销`。
- 计算过程只证明拆分或合计逻辑，不能冒充付款回单。
- 一笔交易可对应多张图，一张图也可对应多笔交易或多个报销类目；保留多对多关系，不强行一图一笔。
- 证据冲突或缺少关键字段时编号询问，不自行设定固定优先级。

## 7. 疑点展示与最终展示分工

- 阶段 A 只展示需要用户判断的疑点图片；每个问题附原图或一次生成的临时局部预览，同图多问题用编号和方位定位。清晰原图足以判断时不额外裁剪。
- 完整逐笔 `图1`、`图2`……对应表由 `batch-output-rules.md` 在本地工作簿验收后统一展示一次。阶段 A 不提前全量展示，后续哈希未变化时也不重复展示。
- 归档原图保持不变。裁剪或标注版本只用于当前对话定位，任务结束后按临时文件规则清理。
- 在相关材料边界未完整检查前，只能说“当前尚未找到”，不能下结论说“没有付款回单”“只有这些问题”或“全部对应”。

## 8. 匿名回归场景

用合成或匿名材料验证规则，不得把私人聊天原图、真实姓名或可识别信息写入 skill 或测试夹具：

- 一张长图顶部有 `60` 元付款区域，另有两笔彼此独立的 `70` 元付款；应识别三笔交易，并在证据支持独立性时核为 `200` 元。
- 两笔金额同为 `70` 元但时间、交易标识或上下文不同；不得仅因同额去重。
- 一笔 `5000` 元回单紧邻对应业务文字；检查必要相邻上下文后应把两者关联，不能仅因回单不在同一气泡内而判定缺失。
- 某项 `810` 元只由业务拆分计算得到；应标为计算依据，除非另有付款凭证，否则不能声称已有回单。
- 出现未预期的 `100` 元充值项目；仍须列入候选并核对，不能因项目类型陌生而漏掉。
