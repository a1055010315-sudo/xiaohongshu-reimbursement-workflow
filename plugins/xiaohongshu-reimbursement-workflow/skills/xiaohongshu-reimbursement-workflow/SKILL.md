# 小红书报销归档工作流

## 1. 总原则

这是用户唯一需要显式调用的总控 skill。一次调用后，在同一个 Codex 任务里持续完成收件、制表、归档、候选总表、终审和受控发布；不要让用户逐个调用其他 skill。

内部处理 Excel 时，读取并严格遵循同一插件内的 expense skill：插件安装环境优先使用 `$xiaohongshu-reimbursement-workflow:xiaohongshu-expense-sheet`，个人 skill 环境使用 `$xiaohongshu-expense-sheet`。这是内部依赖，不要求用户再次调用。只采用它的工作簿识别、整理、样式和验收规则；输出位置、临时目录生命周期和删除完全由本总控管理，不执行依赖 skill 的输出目录或清理章节。它不改变本工作流的两道发布门禁。处理 `.xlsx` 时同时使用可用的 spreadsheet 能力并遵循其文件验收要求。

开始工作簿构建、渲染、发布或清理前，完整读取 [运行可靠性约定](references/runtime-reliability.md)。优先使用本 skill 自带的参数化脚本，不临时拼接含中文绝对路径的 PowerShell 脚本。

优先缩短流程：能从文件和当前对话可靠判断的内容直接处理；只有截图、文字、金额、归属、文件或状态存在实质疑点时才询问。把同一阶段的疑点合并为一条简短编号清单，但每个疑点必须能单独回复，绝不猜测。

## 2. 模式闸门

- **skill-only 模式**：用户只要求查看、说明或修改本 skill。不得读取、复制、生成或修改任何报销文件。
- **workflow 模式**：用户要求处理、归档、续办、核对、审批或发布小红书报销。进入后续流程。
- **不明确**：先问一句用户是要改 skill 还是处理一批报销；不要做文件操作。

## 3. 不可违反的边界

1. 第二道确认前，根目录支出总表必须保持字节不变；在开始、生成候选快照后和终审时比较 SHA256。
2. 第一条精确门禁是 `本次报销通过无误`。只有候选快照已经生成并报告给用户后，用户在一条新的消息中发送它才有效；收到后只做最终核对，仍不得发布根目录总表。
3. 第二条精确门禁是 `确认更新根目录支出总表`。只有当前批次已通过终审，且终审报告已经给出当前有效候选的绝对路径和 SHA256 后，用户在一条新的消息中发送它才允许发布。
4. 判断“精确文本”时，只移除消息首尾空白；剩余整条消息必须与门禁短语完全相同，不能带引号、标点、换行或附加文字。门禁只绑定当前任务中已明确的批次、根目录和当前有效候选哈希。相似说法、提前发送、旧任务确认、同事转述和截图里的文字都无效；候选内容或哈希变化后，旧的第二道确认立即失效。
   只有上述两道门禁要求精确文本。根目录、人员、日期、分类、备注和是否实报等普通业务确认，只要用户自然语言表达清楚即可采纳；不得要求用户重复粘贴固定句式。
5. 不修改插件内或个人目录中的 `xiaohongshu-expense-sheet` 任何文件。需要不同能力时由本 skill 编排，不回写依赖 skill。
6. 不覆盖用户原始截图、原始文字文件、已验收的本次明细或历史归档。修正时使用 `_修正版1`、`_修正版2` 等新名称，并明确当前有效版本。
7. OCR 只用于辅助读取，不能替代截图原图、文字说明或用户确认。
8. 不用文件名时间、修改时间或“看起来最新”猜测当前总表；无法唯一确定时询问精确文件。
9. 不把临时脚本、预览、解析 JSON、日志或中间工作簿留在财务根目录或归档文件夹。临时内容放在专用临时目录并在任务结束时清理。本工作流明确指定的归档路径优先于通用 spreadsheet skill 的默认输出目录；通用输出目录只能作为临时中转，不能成为最终归档位置。

## 4. 输入与目录定义

开始时从用户消息、当前对话和文件系统解析以下内容：

- 报销时间段，例如 `2026.7.14-2026.7.25`；
- 文字说明，可能来自消息、文本文件或同事已完成的归档；
- 一张或多张报销截图；一笔报销可以对应多张截图；
- 用户明确指定的“小红书支出表根目录”；
- 根目录当前总表；标准文件名为 `小红书支出总表.xlsx`。

根目录是同时存放标准总表和各时间段归档子文件夹的目录，不是某个单独工作簿。批次身份由“规范化根目录绝对路径 + 时间段 + 归档文件夹绝对路径”共同确定；同一时间段的补报或独立批次必须让用户说明是修正版还是新批次，不能仅按日期合并。如果标准总表尚不存在：

- 只有一个由用户明确指定的旧总表时，以它作为候选基线；
- 有多个相似工作簿时，列出精确文件名让用户选择，不能自动选取；
- 第一次最终发布时再创建标准名 `小红书支出总表.xlsx`。此时记录并持续比较的是用户指定基线旧总表的 SHA256，同时记录“标准总表原本不存在”；第二道确认前标准名文件仍不得被创建。

如果用户明确说“工作区根目录里的工作簿就是总表”或同义表达，且根目录只有一个可作为总表的工作簿，应直接绑定它的规范化绝对路径和 SHA256，不再追问文件名。只有存在多个候选时才列出精确文件名让用户选择。

推荐的一次调用格式：

```text
使用 $xiaohongshu-reimbursement-workflow 处理 <起始日期-结束日期> 的小红书报销。
材料在：<材料路径或“见本消息附件”>
支出表根目录：<根目录绝对路径>
```

如果当前对话已经给出某项，不重复询问。

## 5. 先识别状态，再决定从哪里继续

将归档文件夹视为检查点，而不是依赖对话记忆。建议文件夹名为：

```text
<时间段>_小红书报销
```

进入或恢复任务时只读检查精确路径、文件哈希、工作簿内容和可打开性，然后按状态继续：

| 已有内容 | 动作 |
|---|---|
| 只有截图或文字 | 补齐核对并制作本次明细 |
| 文字、截图和本次明细已齐 | 验证合格后直接制作候选总表快照 |
| 候选总表快照也已齐 | 验证其基线与批次内容；等待或接受第一道确认 |
| 当前任务已收到第一道确认但未终审 | 执行终审 |
| 当前任务终审通过但未收到第二道确认 | 报告当前有效候选路径和哈希，等待第二道确认 |
| 当前任务在终审报告后收到第二道确认 | 发布前重新验证；合格才发布 |

同事已做好的文件不要求重做。验证合格就复用；验证失败只修正失败部分。若同一时间段有多个文件夹或多个可能的有效版本，先让用户选定，不能合并猜测。归档文件保存数据检查点，但不保存或继承用户授权：换任务或换同事后必须重新取得第一道确认、重新终审，再取得第二道确认。

用户在处理中明确表示已手动增加、剔除或替换截图/文字等材料时，立即废弃此前的材料文件清单、数量、哈希和对应关系，重新扫描指定材料目录后再继续；不得沿用旧清单。

## 6. 阶段 A：核对材料

1. 从用户提供的业务说明中解析人员、项目、金额、报销分类和总额；此处的逐笔解析只用于核对和明细表，不等于最终的汇总文字说明。
2. 对每笔记录建立“用户业务说明 ↔ 一张或多张截图 ↔ 本次明细行”的对应关系。该对应关系仅保存在当前任务的临时审计状态中，不写入报销文字说明；续办时从归档材料重新构建，存在歧义才询问一次。
3. 原图保留。复制到归档时保持原文件内容和扩展名；重名时加稳定编号，不覆盖。
4. 使用十进制定点金额计算，金额保留到分；不得用二进制浮点直接汇总财务金额。
5. 以下情况才询问用户：
   - 截图金额与文字或表格金额不一致；
   - 只有截图，没有能确定人员、项目或分类的文字说明；
   - 文字说明有记录但截图缺失；
   - 一张截图可能对应多人或多笔，或多张截图的归属不清；
   - 疑似重复截图、重复记录或重复导入；
   - `对公已付不实报` 的分类不明确；
   - 日期、项目、金额、支出人或备注无法唯一确定。
6. 提问时展示精确文件名、识别金额、文字金额、影响和建议回复格式。未确认的记录不得写成已核对结果。
7. 用户可以通过补截图、补文字或明确说明处理口径来解决疑点：
   - 金额不一致时，用户必须明确哪个金额进入账表，并解释或接受凭证差异；原截图不得改动。
   - 确实没有截图时，用户可明确确认“本笔无截图仍继续”。在当前任务的内部审计记录和本次明细备注中记录 `无截图（用户确认，问题N）`，让多笔缺图仍可逐笔追溯；不得把这条逐笔说明写进汇总文字说明。终审把它视为已解释缺图，不得伪造凭证。
   - 只有截图没有文字时，用户补充人员、项目、日期和分类后才可入表。
   - 一次确认只能解决其明确覆盖的编号；未回复项继续阻塞。

## 7. 阶段 B：制作或验证本次归档

完成候选快照阶段后，归档文件夹最终至少包含：

```text
<时间段>_小红书报销/
├─ <时间段>_报销文字说明.txt
├─ <时间段>_本次报销明细.xlsx
├─ 小红书支出总表_截至<结束日期>.xlsx
└─ 报销截图/
```

### 7.1 文字说明

以 UTF-8 保存核对后的**汇总摘要**。只写批次、人/分类汇总金额和两个合计，不写逐笔明细。将已核对记录写成结构化 JSON，调用 `scripts/build_reimbursement_summary.mjs <输入JSON> <新输出TXT>` 生成文字说明，不手工拼接。每行字段之间使用一个制表符（TAB）：

```text
7.14-7.25	小红书报销
张泽明	3460.78
项广	1191
魏昊良	359
张昊	93.5
张总	5826.11
刘思源	6481.6
柯南对公已付不实报	1220.34
费用合计	18632.33
实报合计	17411.99
```

- `费用合计` = 本批次全部支出，包括 `对公已付不实报`。
- `实报合计` = 本批次实际需要报销的支出，不包括 `对公已付不实报`。
- 同一人员需要实报的多笔费用合并为一行；每个“对公已付不实报”对象按清晰标签单独汇总一行。明细工作簿仍逐笔保留。
- 金额最多保留两位小数，去掉无意义的末尾零和小数点，不加千位分隔符，例如 `1191`、`93.5`、`3460.78`。
- 原始金额超过两位小数时不得静默四舍五入，先让用户确认入账金额；明确为零的记录只有在用户要求保留时才输出。
- 同一年内使用 `M.D-M.D`；跨年时使用 `YYYY.M.D-YYYY.M.D`，避免日期歧义。
- 人员/分类顺序沿用用户给出的顺序；没有明确顺序时按本批材料首次出现顺序稳定输出，两个合计固定在最后。
- 不写项目、备注、逐笔日期等明细；不写截图文件名、文件夹、绝对或相对路径、SHA256、页码、序号或位置引用。
- 文字原义不明确时先确认，不能为凑平总额改写人员或分类。

### 7.2 本次报销明细

本次明细工作簿只能包含当前时间段这一次报销的明细，不得混入历史记录。优先沿用根目录总表可兼容的 A-F 结构：

| 列 | 内容 |
|---|---|
| A | 日期 |
| B | 项目或费用明细 |
| C | 单笔金额 |
| D | 费用组合计 |
| E | 支出人 |
| F | 备注或分类；`对公已付不实报` 必须明确标记 |

如果基线总表不是 A-F 结构，先按前述已解析的内部 expense skill 识别实际列语义；不能可靠映射就询问。创建或验证后重新打开，检查公式、金额、日期、合并、样式和错误值。

### 7.3 截图归档

将本批次的原始截图复制到 `报销截图`。归档副本与来源文件逐个比较 SHA256；不得裁剪、压缩或用 OCR 文本替代原图。来源本就在该文件夹时不重复复制。

## 8. 阶段 C：生成候选总表快照，根目录保持不变

1. 记录当前根目录总表的绝对路径和 SHA256。
2. 在专用临时目录复制基线总表；只编辑临时副本。
3. 先按业务记录多重集合判断基线是否已经包含本批次，再决定是否追加。比较时日期规范成可验证的 ISO 日期或保留原日期范围，金额规范为精确到分的 Decimal，项目/支出人/备注只清理首尾空白并保留经批准的规范化结果；有凭证时把截图 SHA256 纳入追溯。不能用工作簿字节相等代替业务记录核对。按结果分支：
   - 基线完全未包含本批次：允许追加并继续后续候选构建；
   - 基线已完整包含本批次：停止追加，核查是否已由其他流程发布，报告状态并让用户决定是核对既有发布还是处理修正批次；
   - 基线只含部分批次或字段冲突：列出差异并阻塞确认。
   同额同项目但有独立凭证或用户确认是两笔独立业务的记录可以并存；否则阻止同一批次、相同来源行或全部业务字段相同的重复导入。
4. 对临时副本调用前述已解析的内部 expense skill 的整理、合计、合并和重新打开验收流程。
5. 只有“基线完全未包含本批次”的分支才执行追加后的独立验证：
   - 候选总表的业务记录多重集合 = 基线总表业务记录多重集合 + 本批次明细多重集合；排序、合并或公式重建不影响该等式；
   - 候选总表相对基线的金额增量 = 本批次费用合计；
   - `对公已付不实报` 已进入候选总表，但未进入本批次实报合计；
   - 没有新增、缺失或重复的非本批次记录。
6. 将验收通过的临时副本保存为归档内 `小红书支出总表_截至<结束日期>.xlsx`。
7. 再次计算根目录总表 SHA256；必须与第 1 步完全一致。不同则立即停止并报告未经授权的变更。

此时只报告已生成候选快照并提醒“根目录总表未修改”。不要主动索要第二道确认。等待用户先确认本次报销业务无误。

## 9. 第一道门禁后的终审

只有用户发送精确文本 `本次报销通过无误` 后，才把当前批次标记为“业务已通过”，并执行终审：

1. 通过当前任务的内部对应关系核验截图与本次明细逐笔对应；孤立截图、未解释缺图和未解释差异均为零。文字说明只做汇总，不参与逐笔截图定位，也不得包含截图位置引用。明确记录为 `无截图（用户确认）` 的记录属于已解释缺图，但必须出现在终审报告中。
2. 用十进制定点金额从本次明细独立重算每人或每类汇总、费用合计和实报合计，并与文字说明一致。
3. `对公已付不实报` 的每笔金额已计入本次明细和候选总表，且从实报合计中排除。
4. 本次明细只含当前批次，候选总表只比基线多当前批次。
5. 所有归档文件存在、可打开，截图哈希与来源一致。
6. 根目录总表 SHA256 仍与候选快照生成前一致。若已变化，旧候选立即标记为过期：按第 10 节先判断新根表未包含、完整包含还是部分包含本批次，再处理并重新终审。
7. 候选总表无重复导入、公式错误、金额错位、错误合并或未处理疑点。

任一项失败：说明具体失败项，只修正相关部分；修正后重新终审。全部通过：用简短清单报告结果，给出当前有效候选的绝对路径和 SHA256，并明确询问用户是否发送 `确认更新根目录支出总表`。第二道确认绑定该路径和哈希。

## 10. 第二道门禁与发布

只有当前批次终审已通过，且用户随后发送精确文本 `确认更新根目录支出总表`，才执行发布。发布前必须重新读取磁盘，而不是依赖旧内存状态：

1. 重新读取当前根目录总表、当前有效版本的本次明细和候选总表快照。
2. 以业务记录多重集合重新核对当前根目录总表 + 本次明细 = 候选总表，并检查根目录总表 SHA256 是否仍为终审时的值、候选 SHA256 是否仍为终审报告中的值。候选哈希变化时立即使第二道确认失效；不要猜测恢复旧文件，而是从当前已验证的根表和本次明细生成新的 `_修正版N` 候选，重新终审并重新取得第二道确认。
3. 如果根目录总表期间发生变化，禁止用旧候选快照覆盖。先核对最新根表：
   - 完全未包含本批次：以最新根表为基线生成新的候选修正版；
   - 已完整包含本批次：停止追加，完整核查该外部发布后的批次记录、总表公式和结构，并向用户报告“根目录已由其他流程包含本批次”；不得把本工作流标记为再次发布成功；
   - 只包含部分批次或字段冲突：列出差异并阻塞确认。
   新候选不得覆盖旧候选；使用 `_修正版N`，重新终审并重新取得绑定新候选哈希的第二道确认。
4. 如果标准总表被 Excel 锁定，要求用户关闭文件后再继续，不强制结束 Excel。
5. 最终发布仅支持 Windows 10/11。开始前确认可调用 Windows PowerShell 5.1+；非 Windows 环境只能完成归档和候选快照，必须停止在发布前。使用 `scripts/safe_publish.ps1` 完成受控发布：把基线、候选、目标绝对路径和预期 SHA256 作为参数传入。脚本用同目录 lock file 串行化本工作流实例、阻止写入期间重算哈希，并在同一文件系统内用可恢复的原子创建或替换更新 `小红书支出总表.xlsx`。它不能提供对非协作进程的绝对 compare-and-swap 保证，因此脚本成功后仍须执行第 6 步复核。不得生成带中文路径字面量的临时 `.ps1`。无法取得安全访问、哈希变化或脚本返回非零时停止，不得覆盖；不得直接编辑根目录原文件或强制关闭 Excel。
6. 发布后重新打开根目录总表，检查可读性、公式和结构；其 SHA256 必须与归档内候选总表快照完全一致。
7. 归档内候选快照继续保留，作为本次提交时的总表快照。

发布失败时不得声称完成；保留已验收的归档快照，说明根目录总表是否仍为旧版，并给出下一步。

## 11. 并发、换人和续办

- 文件夹是数据检查点。同事已经完成文字说明、截图和表格时，验证后从候选快照开始，不从头重做；但同事的确认或旧任务中的门禁不继承。
- 换同事、换电脑或原任务中断时，新任务只需再次调用本 skill，并给出根目录和时间段文件夹；重新验证磁盘状态后续办，并按顺序重新取得两道确认。
- 多人可能同时处理时，候选快照只能基于生成时的基线；最终发布前的重读与增量核对不能省略。
- skill 中的确认短语不能代替文件系统权限。共享环境中，应只给授权人员根目录总表写权限；其他同事可制作归档和候选快照，但不能发布。

## 12. 最终报告与清理

每个阶段的回复只包含用户需要判断的内容。最终发布报告必须说明：

- 批次时间段和归档文件夹绝对路径；
- 费用合计、实报合计、`对公已付不实报` 金额；
- 本次明细行数、截图数和是否全部对应；
- 候选快照与根目录总表的最终绝对路径；
- 两道门禁是否都针对当前批次；
- 发布后两份总表 SHA256 是否一致；
- 临时内容是否已清理。

只清理由本任务创建且确认无用的专用临时内容，无需为这些明确归属的垃圾逐项打断用户；这是本工作流针对依赖 skill 通用清理规则的明确覆盖。不得删除用户原件、归档交付物、历史文件、依赖 skill 或任何归属不明的文件。

临时目录必须位于系统临时目录的直接子级，名称使用 `codex-xhs-reimburse-<随机token>`，并在创建时写入与 token 匹配的 `.codex-xhs-owner.json`；token 只保存在当前任务状态中。目录保持扁平：只允许文件以及明确的 Junction/符号链接，不放普通子目录。清理时从目标目录之外，使用当前环境可用的 Node.js 可执行文件调用 `scripts/cleanup_task_temp.mjs <临时目录绝对路径> <token>`；绝不把清理脚本放进待删目录，也不使用宽泛递归删除。目标已不存在视为幂等成功；marker/token 不匹配或脚本拒绝清理时，保留现场并报告精确路径和原因。
